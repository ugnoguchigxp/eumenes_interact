# eumenes_interact 品質改善実装計画

作成日: 2026年11月5日。状態: 実装・段階検証中。同日の追加依頼により、Claude APIとOpenAI APIのLunaを使う検証を含む。

技術品質を同じ評価基準で80点以上に引き上げるため、完了と取消の整合性、LLMによる判断、配布と統合、継続的な検証を順に整える。対象はブラウザ操作基盤であり、個別サイトの追加で成功例を増やす進め方は採らない。

基準は commit `a38f9553acf56715a8c29e170c59ca1829558a4c` の多角的評価。技術品質は暫定49.1点、根拠充足率95.0%、未確認項目を含めた幅46.7〜51.7点。プロジェクトの可能性は根拠充足率76.7%で総合点を保留した。80点は目標であり、実装完了だけで達成したとは扱わない。

設計の正本は [plan.md](../plan.md)。本書は改善作業と検証の管理に使う。旧Arm 0の記載や担当登録の粒度など、現行実装と設計内の記載が競合する事項はT00で整理する。未決事項を推測で実装しない。

## 守る設計と変更方針

意味理解、計画、開始先、回答の充足、対象の選択はLLMが判断する。コードは構造化出力、参照の存在、URL、権限、予算、状態遷移、外部入出力を検査する。意味判断の専用分岐、サイト名辞書、正規表現、固定文言の追加で回帰例を通さない。

現時点の `InferencePort.complete` は構造化出力を受け付け、Claude接続にも実装がある。OpenAIへの直接接続は未実装で、既存LARM接続は構造化出力を拒否し、接続先もローカル用に制限している。T24で同じ推論portへ最小のOpenAI接続を足し、LARM用の接続制限は緩めない。一方、隣接repoの `planSteps` は語句と文分割で計画する関数であり、そのまま呼び続けてもLLMによる計画にはならない。T07では既存の推論portを計画・段の判断・要約に共通利用し、既存の行動契約とFact・予算関数を残す。共通契約で不足する部分だけを小さく追加する。

| 残す機構 | 改善時の確認 |
| --- | --- |
| 純粋な1手の核とホスト所有DB | 核に時計・ファイル・Bun API・製品domainを持ち込まない |
| 送出前のcommitと操作台帳 | 外部操作が届いた可能性を保存し、不明結果を無条件に再送しない |
| 承認の再検査 | 許可は所有者・操作・対象・値・世代・期限に結び付ける。モデルの申告だけで許可しない |
| 既知の項目IDと結果ID | IDを推測・再利用して別対象を操作しない。曖昧さは候補として返す |
| 値の出所と保存制限 | ページ由来の命令や値で権限を増やさない。利用量不明を0としない |
| 部分結果と独立scorer | 確認できた範囲を返し、モデルの自己申告だけで成功と採点しない |

専用実装が必要な場合は、外部仕様、再現可能な失敗、測定結果、安全要件のいずれに対応するかを変更説明に残す。URL解析、IP範囲検査、MCPの応答解析、OSのプロセス識別はこの範囲に入る。ユーザーの意図の分類を専用実装へ移さない。

## Claude APIとOpenAI API Lunaの検証

実LLMの検証は両APIを必須の比較対象とする。Claudeは既存の `claude-haiku-5-5` を初期候補として維持し、OpenAIは利用者が指定したLunaを使う。2026年11月5日に確認した正式なLunaのモデルIDは `gpt-6-luna` で、Responses APIと構造化出力に対応している。[OpenAIのモデル仕様](https://developers.openai.com/api/docs/models/gpt-6-luna)

| 検証方式 | 用途 | 着手条件 |
| --- | --- | --- |
| scriptedと推論stub | コードの契約、部分・結合・通し、障害注入、CI | APIキー不要。実LLMの判断精度とは区別する |
| Claude API | 実際の計画、部品選択、復旧、質問、完了判定 | T24の接続適合試験、モデルと予算の固定、実行指示 |
| OpenAI API Luna | Claudeと同じケースと安全境界での実LLM検証 | T24の接続適合試験、`gpt-6-luna`の利用可否、モデルと予算の固定、実行指示 |
| manual | 再現と原因調査の補助 | 人の回答、URL補完、形式修正を介入として記録し、自律成功へ混ぜない |

### API接続と設定

| 項目 | Claude API | OpenAI API Luna |
| --- | --- | --- |
| 接続 | 既存のMessages API接続を再利用 | 既存InferencePortへResponses API接続を追加 |
| 初期モデル | `claude-haiku-5-5`。変更する場合は別条件として固定 | `gpt-6-luna`。他モデルへ自動で置き換えない |
| 構造化出力 | 現行の `output_config.format` を検証 | `text.format` のJSON Schemaを共通契約から生成して検証 |
| 初期effort | 既存設定の `low` を候補として利用可否を確認 | `reasoning.effort: low` を初期比較条件とする |
| APIキー | `.zprofile`の `CLAUDE_API_KEY` を `ANTHROPIC_API_KEY` として引き継ぐ | `.zprofile`の `OPEN_AI_API_KEY` を `OPENAI_API_KEY` として引き継ぐ |
| 設定と結果 | provider、要求modelと返却model、SDK/API、effort、出力上限、timeout、retry、cache、処理tierと価格根拠を記録 | 同左。返されない情報はnullとして扱う |

公式仕様に従った要求と結果の変換だけをprovider接続へ閉じ込め、操作の意味判断、部品、承認、完了契約は共通化する。両社のSchema差は共通契約の範囲で吸収し、APIが受理するJSONになっても、手元の契約検査は省略しない。[OpenAIの構造化出力](https://developers.openai.com/api/docs/guides/structured-outputs)、[Claudeの構造化出力](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

Lunaでは本文のJSONを受け取る構成を初期実装とし、組込みの検索・computer use・remote MCP等を有効化しない。ブラウザ操作は既存の権限境界を通す。provider固有の拡張機能を比較中に片側だけへ与えない。

### キーとデータと予算

キーは利用者が `.zprofile` に設定済みの2変数を共通利用する。同ファイルには標準名への変数参照を追加済みで、新しいログインシェルで認識を確認した。実際の値を計画書や別ファイルへ複写していない。標準名がすでに設定されていればその値を優先する。

- [ ] プロジェクト別の `.env` を必須にしない。起動時に標準名または既存の別名を環境変数から取得し、別名だけならprocess内でproviderへ渡す。既存の標準名を上書きしない。
- [ ] キーはチャット、計画書、experiment、DB、ログ、撮影、manualファイル、browserの子processへ複写しない。キーの有無だけを診断し、値を表示しない。
- [ ] 起動元の環境が古い場合はログインシェルから起動し直す。既存ターミナルでは `source ~/.zprofile` で読み直せる。CLIが `.zprofile` をデータとして解析したり、毎回自動で実行したりする実装は追加しない。
- [ ] API利用可否は実行前の小さな接続確認で判定する。401・403・利用不可model・非対応設定ならその条件を停止し、別モデルや別providerへ黙って切り替えない。
- [ ] 各providerと全体の金額上限、HTTP試行上限、論理推論回数、出力token上限、timeoutをexperimentへ固定する。T03の段と全体の予算に計画・要約も含める。
- [ ] SDKとhostの二重retryを避ける。実際のHTTP送信回数、retry待機、429・5xx・接続断を別に記録し、再試行も予算内で行う。送信後にusageが不明な呼出しを0円と扱わない。
- [ ] 利用時点の公式単価と最大入力・出力の条件から保守的に枠を予約する。上限内か判断できない状態では次の課金呼出しを止める。費用表示は推定と確定可能な使用量を区別する。
- [ ] APIへ渡すのは人工fixtureまたは指示された実サイトの必要な観測だけとする。JSON Schemaの説明やenumへ秘密・個人情報を埋め込まない。保持設定とデータ送信先を実行条件へ記録する。

この追加依頼では共通環境の別名設定と認識確認まで行い、実APIの送信と課金は行っていない。実行時には、すでに指示された対象と予算で進め、条件を変える必要があるときだけその差を示す。

### 比較と合格条件

- [ ] まずAPI接続をstubで試験し、次に両APIで同じ人工fixtureを動かし、最後に実サイトと最終holdoutを実行する。各段階の結果を混ぜない。
- [ ] モデルごとに変更前と変更後を比較する。Claudeの旧結果とLunaの新結果だけを比べて、実装の効果とモデルの差を混同しない。旧snapshotにOpenAI接続がないため、接続・設定・計測だけを加えた比較用checkoutを別に固定し、その差分を残す。基準の評価記録は変更しない。
- [ ] provider間では同じ実装版、ケース、Skill、操作部品、権限、到達条件、利用量上限、browser、初期状態、反復数を使い、実行順を交互にする。同名effortやtoken数が同じ計算量を意味するとはみなさず、設定と実費を併記する。
- [ ] 実装の前後比較ではケース・model・権限・到達条件・予算を固定し、変更したSkillや契約も改善内容として版と差分を残す。新機能のケースは共通機能の比較と分ける。
- [ ] 初期のAPI別smokeは、単段検索、複数段、browser不要、曖昧さと続行、失敗後の完了、取消、注入、予算境界を含む8種とする。T19で独立ケースと反復を増やす。
- [ ] 必須契約違反は両providerで各0件。モデルの不得意なケースを除外せず、成功率・誤対象・復旧・質問・使用量・時間・429・拒否・形式不正・人の介入をprovider別に出す。
- [ ] 判定の正本はfixture側の到達状態と独立した受入基準に置く。ClaudeとLunaを相互の補助採点に使う場合は、試行主体を伏せ、自己採点と区別し、不一致を人が確認する。補助採点の費用と結果も別記録する。
- [ ] 片方だけで成功した場合は対応範囲と理由を残し、両APIの受入完了とはしない。APIの利用不可・429・timeoutを成功例だけの比較から黙って消さない。

モデルの固定には実際に指定できるsnapshotを優先する。aliasしか提供されない場合は要求ID・返却ID・日時・返却される識別情報を保存し、内部版まで固定できたとは主張しない。詳細な比較条件を [API検証の計画](reviews/2026-11-05/api-evaluation-plan.json) に置く。Claude側の利用モデルは実行時の公式一覧と利用可能範囲も確認する。[Claudeのモデル一覧](https://platform.claude.com/docs/en/models/overview)

## 検証の実行方法

各項目で部分、結合、通しの順に行う。対象コード・依存・設定のsnapshotを固定し、結果が出るまで編集しない。失敗を再試行する場合は前回から変わった条件を記録する。

| 層 | 実行例または対象 | 合格条件 |
| --- | --- | --- |
| 部分 | `bun test packages/eumenes-interact/test/core packages/eumenes-interact/test/sqlite packages/eumenes-interact/test/definitions` と各項目の対象test | 契約の正負の条件、境界、状態が一致 |

| 依存と配布 | `bun run check:stack`、`bun run check:collab`、`bun run check:dist`、T10の成果物導入検査 | 固定版と実内容が一致し、全公開部分が利用可能 |

| 実LLMとholdout | T19で事前に固定したexperiment | 全試行、介入、違反、利用量、失敗分類を記録 |

| Eumenes | T17で確定する対象domainと結合試験 UI E2E | 会話から結果採用までと切戻しを受入 |

実行例の一時DBとChromeパスは実行環境で解決する。資格情報や本番DBをfixtureへ渡さない。`check:stack`のEumenes参照先は読み取り専用で明示し、そこで見つかった担当外の問題は証拠と影響を報告する。

文書だけを変更した場合はリンク、JSON、採点の計算、指摘の対応、差分を検査する。製品の動作を変えていないため全試験の再実行を省略できるが、省略理由を記録する。

## プロジェクト評価への対応

技術品質80点とプロジェクトの可能性80点を同一視しない。後者は利用結果や維持体制で再評価する。新規性が限定的でも、内部の問題価値や利用効果が高い選択は成立する。

| 観点 | 作業と必要な証拠 |
| --- | --- |
| problem | T19 T20。具体的な反復課題、従来負担、実装担当以外の利用観察 |
| solution | T02 T07〜T10 T16 T18〜T20。通常と失敗の達成、導入から価値までの実行、比較結果 |
| differentiation | T18 T20 T22。同じ条件の代替比較と、選ぶ理由・不利な条件 |
| novelty | T08 T09 T22。既存手法との相違とその実用効果。新しさを作るための機能追加はしない |
| adoption | T06 T16 T18 T20。導入・移行・支援負担、利用先への経路、継続利用 |
| defensibility | T10 T19 T21 T22。更新できる検証資産、代替可能性、維持する動機と資源 |
| execution | T00 T15 T19 T21。実際の納品、担当と見積に合う優先順位、失敗から改善した証拠 |
| timing | T06 T18 T20 T22。実行時点の依存と利用環境、導入時期、変化への応答余力 |
| health | T10 T15 T21。責任者と引継ぎ、必要な更新、意思決定と継続資源の実績 |
| expansion | T14 T18 T20〜T23。隣接用途の需要と再利用、追加費用、段階ごとの着手と撤退条件 |

利用や資源の確保に依存する項目は、コード実装の完了に含めて偽装しない。確認できなければ総合点は引き続き保留する。

## 再評価と停止条件

- [ ] 各段階の終了時に、変更commit、依存と環境、実行コマンド、exit、全試行の結果を保存する。基準記録と混ぜない。
- [ ] F01〜F08の受入に加えて、新しいHigh以上の問題がないかを調べる。未解決の疑いは未確認として残す。
- [ ] 技術30項目すべてへ実際の根拠を付け、段階3と4には反証確認を、4には強い実行または独立観察の証拠を付ける。
- [ ] 変更後は `assessment_kind: re-evaluated`、実際の新snapshot、同じprofileと重みで再計算する。目標資料の値を実測台帳へコピーしない。
- [ ] 正式技術評価80.0点以上、必須契約、検証、配布と統合の完了条件を満たしたときだけ80点達成とする。充足率が変わった比較では共通評価項目の差も示す。
- [ ] プロジェクトの可能性はT20〜T22の実績を別台帳へ追加して再評価する。得点不足の理由が需要・定着・新規性なら、コード量を増やす前に用途と計画を見直す。

同じ目的の試行は「仮説・実施・結果確認」の一組を1ラウンドとし、3ラウンドで俯瞰する。根拠のない同じ失敗の反復、検証中の編集、最新計画からの逸脱があれば次の編集・再実行前に見直す。新しい証拠、減った残作業、未解決の仮説を確認し、継続・方針変更・完了・阻害要因の報告を選び、この会話へ短く通知する。

正常に進む長時間処理は経過時間だけで止めない。担当外、依存先の変更待ち、実行権限、利用者や検証環境の未確保が阻害する場合は、完了済みの差分、未解決事項、続行条件を残す。要件や試験期待を弱めて先へ進まない。
